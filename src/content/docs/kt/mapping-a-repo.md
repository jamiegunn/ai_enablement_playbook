You are here if: the quick start's map of `ledger-api` is stamped and the next repo is `ledger-core`, twelve times bigger and half-migrated; or you skipped the quick start because one page on the *why* is worth more to you than one artifact; or someone handed you an AI-generated architecture doc and asked whether it can be trusted.

A repo map is the set of answers a senior engineer would assemble on their first day with a codebase, if they had the day — with a pointer into the code next to every answer. *What is this and what isn't it? Where does execution start? What happens to one request, file by file? What data does it own? What does it talk to? How do I build it? What will surprise me? Where can I make a first change without breaking anything?* Eight questions. The answers are cheap to generate and worthless on their own; **the pointers are the product**, because `SettlementCalculator.java:142` can be checked in twenty seconds and a paragraph about "the settlement layer" cannot. This page is the Map stage of the [pipeline](/kt/overview/) for one repository. It pulls the context lever (the map is what every later session loads) and the proof lever (the citation, then the stamp).

The subject is `ledger-core`: 410,000 lines of Java, Spring Framework 5, a Java 8 → 17 migration that stopped halfway, and a main-developer share of 71% Priya.

## The skill, and why each line is there

The whole method fits in one file. It's the same `map-repo` skill the [quick start](/kt/quick-start/) runs; a **skill** is a procedure you invoke by name (`/map-repo`), stored as markdown with frontmatter that says what it may do ([Skills](/toolkit/skills/) owns the format). Here it is in full:

```markdown
---
name: map-repo
description: Map this repository into docs/ARCHITECTURE.md (DRAFT) — entry points, request path, data model, integrations, build & run, surprises — every claim cited path:line, unknowns listed as unknowns. Use when onboarding or when asked "how does this repo work".
disable-model-invocation: true
allowed-tools: Read Grep Glob Bash(./mvnw *) Bash(git log *) Bash(find *)
---
You are mapping this repository for a senior engineer joining the team who has
never seen it. Write `docs/ARCHITECTURE.md`. Its first line is:
`**Status: DRAFT — not yet reviewed by a named expert.**`

Rules that override everything else:
1. Every factual claim ends with a citation `(path:line)` or `(path:line-line)`.
   A claim you cannot cite goes under "## Unverified" with what would confirm it.
2. Search, don't read: use Grep and Glob to find things; read only the files you
   cite. This repository may be very large.
3. "No callers found" is a finding; "unused" is a conclusion. Report the finding.
4. Two toolchains may coexist (Java 8 and 17 profiles, .NET Framework and .NET 8).
   Say which one CI actually runs, citing the workflow or build file.
5. Never invent a class, method, table, queue, or endpoint name. If a name
   appears only in documentation and not in code, say exactly that.

Answer these eight questions, each as a `##` section, in this order:
1. What is this, in one paragraph — and what is it NOT (what lives in
   neighbouring repositories)?
2. Entry points — every way execution starts: HTTP endpoints, message listeners,
   scheduled jobs, CLI mains. A table: entry → handler `path:line` → what it
   calls next.
3. The request path — trace ONE representative request end to end, file by file.
4. Data — the domain model and where it is persisted; every table and queue
   touched, with the code that touches it.
5. Integrations — every external system (databases, queues, HTTP clients, file
   drops): the config key, the code, the direction of data.
6. Build, run, test — the exact commands from the build files and CI, and what
   they require (environment variables, services, credentials by name only).
7. Things that will surprise you — anything a senior engineer would want to be
   warned about: dead-looking code with live callers, reflection or DI wiring,
   generated code, feature flags, dual toolchains, time-zone handling.
8. Safe places to make a first change — three candidates with test coverage,
   cited.

Then two more sections: "## Unverified" and "## Questions for the expert" —
the things only a human can answer (why, history, intent).

Keep the whole file under 400 lines. Prose is cheap; citations are the product.
```

Why each part is there:

- **`disable-model-invocation: true`** — only a human runs this. A map is a deliberate act with an expert's thirty minutes booked behind it, not something the model starts because a question sounded like "how does this work".
- **`allowed-tools`** — search and read, plus exactly three commands: the build (question 6 must be *run*, not copied from a README), `git log` (to date things — "untouched since 2018" is a `git log` fact), and `find`. No `Write` is deliberate: interactively you approve the one write of `docs/ARCHITECTURE.md`; headless, the run command grants it.
- **The DRAFT status line** — the stamp is a git event that hasn't happened yet, so line one says so. Sam's session will read that line.
- **Rule 1, cite or confess** — the proof lever. An "Unverified" entry that says *what would confirm it* turns a gap into a task for the expert instead of a guess for Sam.
- **Rule 2, search, don't read** — 410,000 lines is several times any context window as of September 2026 ([why](/start/how-agentic-coding-works/#tokens-and-the-cost-shape)). The map reads perhaps a twentieth of the repo, which is what makes it affordable.
- **Rule 3, finding versus conclusion** — the `MoneyMath` lesson, below. "No callers found" says where the agent looked; "unused" tells someone to delete a class wired by reflection.
- **Rule 4, name the live toolchain** — half-migrated repos build two ways, and only one is real. The workflow file is the evidence.
- **Rule 5, never invent** — the `FxConversionService` failure ([the mechanism](/start/how-agentic-coding-works/#why-it-makes-things-up)). A name that exists only in Confluence is a finding about Confluence.
- **The eight questions, in that order** — the order a senior engineer asks them: what is it, where does it start, follow one request, then data, edges, build, surprises, and only then "where do I begin".
- **The two extra sections** — "Unverified" is the agent's honesty; "Questions for the expert" seeds [the interview page](/kt/expert-interviews/) and is the only part of the map that costs an expert's hour.
- **Under 400 lines** — the unit of review is thirty minutes. A longer map isn't more complete; it's unreviewable, and an unreviewed map is a `DRAFT` forever.

## How the agent explores

Two things happen when you run the skill, and it's worth knowing both so the output makes sense.

**It searches; it doesn't read.** The [loop](/start/how-agentic-coding-works/#the-loop) greps for a term, reads sixty lines of the file that matched, greps for what it found there, and so on. A 410,000-line repo is never in the window; a few hundred lines of it are, at a time. Claude Code ships a built-in `Explore` subagent — a delegate built for exactly this search-and-summarize work — and the main session will often hand it "find every entry point" on its own.

**It fans out, one delegate per question.** A **subagent** is a worker with its own fresh context window that does one job and returns a summary, not its transcript ([Subagents](/toolkit/subagents/) owns the mechanics). Eight questions in one window means the entry-point grep output is still in context while the model traces the request path; eight subagents means a clean window per question and eight cited summaries for the parent. The built-in `Explore` doesn't know the eight questions or the citation rule, so define one that does — the `description` is what the model matches on when deciding to delegate:

```markdown
---
name: repo-question
description: Answers ONE of the eight repo-map questions for the current repository by searching (never reading whole files) and returns a summary in which every line carries a (path:line) citation. Use when mapping a repository — one instance per question.
tools: Read Glob Grep
model: sonnet
maxTurns: 20
---
You answer exactly one repo-map question, given in the request. Grep and Glob
first; Read only the lines you will cite. Every line of your answer ends with
`(path:line)` relative to the repository root. If you cannot find something,
write "not found: <what you searched for, where>" — never a plausible name.
Never cite anything under target/, build/, bin/, or obj/. Return at most 60
lines: the parent will merge eight of these into one document.
```

Save it as `.claude/agents/repo-question.md`. `tools: Read Glob Grep` means a subagent can answer but never write — the parent writes the one file. `maxTurns: 20` is a bound: a question that hasn't converged in twenty searches is looping, and its summary will say what it couldn't find. `model: sonnet` because search-and-cite is exactly what the default model is for; the trade-off table at the end says when to reach for `opus`.

Headless, the same definition rides along as inline JSON — the same fields keyed by agent name, with the body as `prompt` — so a CI runner needs nothing under `.claude/agents/`:

```bash
# seat: team
cd ~/ledger/ledger-core
claude -p "/map-repo" \
  --permission-mode acceptEdits \
  --allowedTools "Read,Grep,Glob,Write,Edit,Bash(./mvnw *),Bash(git log *),Bash(find *)" \
  --max-turns 60 \
  --max-budget-usd 8 \
  --model sonnet \
  --agents '{"repo-question": {"description": "Answers ONE of the eight repo-map questions by searching and returns a summary in which every line carries a (path:line) citation. Use when mapping a repository — one instance per question.", "prompt": "You answer exactly one repo-map question. Grep and Glob first; Read only the lines you will cite. Every line ends with (path:line). If you cannot find something, write not found: <what, where>. Never cite target/. Return at most 60 lines.", "tools": ["Read", "Glob", "Grep"], "model": "sonnet", "maxTurns": 20}}' \
  --output-format json > map-run.json
```

(Without `--agents`, that command is exactly the quick start's headless run; the flags — `acceptEdits` so the one write goes through, sixty turns and the budget from the [site's table](/kt/measurement-and-governance/) — are read field by field in [Running Claude Unattended](/overnight-qa/running-unattended/).) Interactively it's `claude` in the repo, then `/map-repo`. Either way the trace looks like this, reconstructed from a session on `ledger-core`:

```text
turn 1   parent → Glob "pom.xml" ".github/workflows/*.yml" "Jenkinsfile"     → 4 files
turn 2   parent → repo-question × 8, in the background: Q1 what-is … Q8 safe first change
           Q2   → Grep "@RequestMapping|@JmsListener|@Scheduled|static void main" src/main   → 14 hits, 9 files
           Q2   → Read src/main/java/com/ledger/core/sweep/ReconciliationSweep.java (40–70)
           Q7   → Grep "class=\"com.ledger" src/main/resources                             → 6 hits in 1 XML file
           …
turn 3   parent ← 8 summaries, each ≤ 60 lines, every line cited
turn 4   parent → Bash ./mvnw -q -DskipTests package     → BUILD SUCCESS  (question 6 is run, not copied)
turn 5   parent → Write docs/ARCHITECTURE.md              → 371 lines
```

:::note[What the model sees]
The repo's `CLAUDE.md` (the Day-1 three sections), the skill text, and whatever the tools bring back. Not Confluence — nothing on this page connects to it, on purpose. A map built from the code alone can be checked against the code alone; a map that read the "Settlement Flow" page inherits its 2019.
:::

## The eight questions, with good answers

What a good answer looks like, and the `ledger-core` answer the skill actually produced, one question at a time.

**1. What is this — and what is it NOT.** Good: one paragraph, and a second one naming the neighbours. The "NOT" half is what saves Sam an afternoon. `ledger-core` is the settlement engine: it computes, posts, and reverses settlement entries against the Oracle `LEDGER` schema `(src/main/resources/ledger-core.properties:9)`. It has no HTTP endpoints (that's `ledger-api`), no queue listeners (`ledger-mq-bridge`), no DDL (`ledger-db`), and does not own the 03:00 run (`ledger-batch` calls it) — each stated as a search that found nothing, cited.

**2. Entry points.** Good: a table, one row per way execution starts, including the rows that say "none". This is the excerpt Priya read first:

```markdown
## 2. Entry points
| Entry | Handler | Calls next |
|---|---|---|
| Public service bean — callers are in other repos (inference; see Unverified) | `SettlementService.settle()` (src/main/java/com/ledger/core/settle/SettlementService.java:57) | `SettlementCalculator.settle()` (src/main/java/com/ledger/core/settle/SettlementCalculator.java:142) |
| Public bean | `FxRateCache.update()` (src/main/java/com/ledger/core/fx/FxRateCache.java:31) | — |
| `@Scheduled(cron = "0 15 4 * * *")` | `ReconciliationSweep.run()` (src/main/java/com/ledger/core/sweep/ReconciliationSweep.java:52) | `SettlementBatchDao.findUnreconciled()` (src/main/java/com/ledger/core/persist/SettlementBatchDao.java:40) |
| CLI main | `ReplayMain.main()` (src/main/java/com/ledger/core/tools/ReplayMain.java:19) | `SettlementService.settle()` — no callers of this main found in .github/, Jenkinsfile, or scripts/ |
| HTTP endpoints | none — Grep `@RequestMapping\|@GetMapping\|@PostMapping` under src/main: 0 hits | (ledger-api) |
| Message listeners | none — Grep `@JmsListener\|MessageListener` under src/main: 0 hits | (ledger-mq-bridge) |
```

The rows that say *none* with the search that proved it are worth as much as the rows with handlers.

**3. The request path.** Good: one request, file by file, each hop cited, ending at the store. A settlement request enters at `SettlementService.settle()` `(…/settle/SettlementService.java:57)`, is validated `(…/settle/SettlementRequestValidator.java:30)`, priced in `SettlementCalculator.settle()` `(…:142)`, has FX applied in `FxApplier.apply()` `(…/fx/FxApplier.java:88)` with the rate from `FxRateCache` `(…:31)`, is rounded by `MoneyMath.round(amount, HALF_EVEN)` `(…/settle/SettlementCalculator.java:151)` — a class from `ledger-shared` — and lands as rows in `LEDGER.SETTLEMENT_POSTING` `(…/persist/SettlementPostingDao.java:73)`. Seven hops, seven pointers.

**4. Data.** Good: the domain classes and *every* table and queue touched, with the touching code. `SettlementRequest`, `SettlementBatch`, `Posting` `(src/main/java/com/ledger/core/model/)`; tables `LEDGER.SETTLEMENT_POSTING` `(…/persist/SettlementPostingDao.java:73)`, `LEDGER.SETTLEMENT_BATCH` `(…/persist/SettlementBatchDao.java:40)`, `LEDGER.FX_RATE` `(…/fx/FxRateDao.java:27)`; one stored procedure, `LEDGER.PKG_SETTLE.POST_BATCH` `(…/persist/SettlementBatchDao.java:88)`. Queues: none in this repo — with the search cited.

**5. Integrations.** Good: config key → code → direction. Oracle via JDBC: `ledger.db.url` `(src/main/resources/ledger-core.properties:4)`, read and written. That's the only external system in the code, and the map says so rather than listing MQ because everyone knows Ledger uses MQ.

**6. Build, run, test.** Good: the commands CI runs, cited to the workflow, and what they need by name. `./mvnw -B -Pjdk17 verify` `(.github/workflows/build.yml:23)`; integration tests need `LEDGER_DB_HOST` and `LEDGER_DB_SERVICE` `(src/main/resources/ledger-core.properties:4)`. The build was run during the map, so the line is verified, not transcribed.

**7. Things that will surprise you.** Good: the list a senior engineer would want on day one, every item cited. For `ledger-core`: the two toolchains, the XML bean file that wires a "dead" package by string, the JAXB classes that don't exist until you build, the sweep at 04:15 that nobody mentions, `HALF_EVEN` in Java against Oracle's `ROUND` on the PL/SQL side. Each is a hazard below.

**8. Safe places to make a first change.** Good: three candidates *with test coverage cited*, not three easy-looking files. `FxApplier` (22 tests, `src/test/java/com/ledger/core/fx/FxApplierTest.java:1`), `SettlementRequestValidator` (17 tests, `…/SettlementRequestValidatorTest.java:1`), `Posting` (11 tests, `…/model/PostingTest.java:1`). This section becomes Sam's first ticket on [the onboarding track](/kt/onboarding-track/).

Then "Unverified" (who calls `SettlementService.settle()` — the callers are in other repos; whether `ReplayMain` is ever run) and "Questions for the expert" (why `HALF_EVEN` here and `ROUND` there; whether Jenkins still runs).

## The citation rule

Every factual sentence ends with `(path:line)` or `(path:line-line)`: the path relative to the repo root, the file with its extension, no spaces — exactly that shape, because a script parses it. The nightly freshness check in [Keeping It True](/kt/living-docs/) greps `docs/**/*.md` for that pattern and fails when the file is gone or the line number exceeds the file's length; a citation written as `FxApplier.java line 88` is invisible to it, and so to the thing that keeps the map true.

Three corollaries. **Never cite a document** — a Confluence page or a README is a claim, not evidence; a claim sourced only to a document goes under "Unverified" saying so. **Never cite `target/`** or anything else a clean clone doesn't contain. **A citation is not a proof; it's a pointer to one.** The reviewer opens ten of them and checks that the line says what the sentence says — the only check that takes thirty minutes instead of a week.

## What makes legacy hard

The skill's rules 3, 4, and 5 exist because of these five things. Each is a paragraph on the hazard and the behaviour you want from the map.

### Two toolchains

`ledger-core` builds two ways: a `jdk17` profile and a `jdk8` profile `(pom.xml:212)`. The map must say which one is *real*, and the evidence is the workflow, not the README: `.github/workflows/build.yml:23` runs `-Pjdk17` and nothing under `.github/` invokes `jdk8`. But there's also a `Jenkinsfile` at the root that calls `-Pjdk8 deploy` `(Jenkinsfile:14)`, last changed in 2021 per `git log`. A good map writes exactly that — GitHub Actions runs 17; a Jenkins pipeline referencing 8 exists and its status is unknown — and puts "does Jenkins still run?" under Questions for the expert. A bad map picks one.

### Generated code

The settlement-file classes under `com.ledger.core.io.generated` don't exist in the repo. They're produced at build time by the JAXB plugin `(pom.xml:143)` from `src/main/xsd/settlement-file.xsd`. An agent that reads a built checkout will happily cite `target/generated-sources/…:40`; a clean clone has no such file, the freshness job flags it on night one, and Sam can't find it. The rule: cite the schema and the plugin configuration, and say the classes are generated.

### Dead-looking code

`ledger-shared` has forty classes nobody has opened since 2018 and one, `MoneyMath`, that everything routes through. Grep `ledger-core` for those forty and you'll find no callers — and "no callers found" is the correct sentence. **"No callers found" is a finding; "unused" is a conclusion.** The finding says where you looked: *no references in `src/main/**/*.java`*. The conclusion invites someone to delete them, and the very next hazard is why that's dangerous. The map lists the forty with the finding, dated by `git log`, and moves on.

### Reflection and DI wiring

Spring wires by annotation, by XML, and by string. `CoreContext` scans `com.ledger.core` `(src/main/java/com/ledger/core/config/CoreContext.java:18)`, so any `@Component` in the tree is live without a single Java reference to it. And `core-legacy-beans.xml` declares `ManualAdjustmentPoster` by class name `(src/main/resources/META-INF/spring/core-legacy-beans.xml:27)` — a class in the `legacy` package with, by Java-source grep, no callers. That's the trap in the previous paragraph, sprung. The map must **find** the wiring, not guess at it: grep the simple class name across *all* file types, not just `.java`, and cite the XML line. If the map says "wired by Spring" without a pointer, it's inference and gets labelled.

### The Oracle side

The real architecture of Ledger is partly in the database, and `ledger-db` is not a Java repo: 1,200 PL/SQL objects, Liquibase for everything since 2022 (`db/changelog/db.changelog-master.xml`), and everything older as `.sql` files in a folder called `legacy/DO_NOT_RUN`. Mapping it is the same skill with three sources. The Liquibase changelogs are the citable record for anything from 2022 on. The `legacy/` folder is citable but undated — `git log` shows the 2021 migration commit for all of it, so the map says "present in `legacy/DO_NOT_RUN/pkg_settle.sql:214`; created before 2021; whether it matches the deployed object is unverified". And for the objects created by hand in 2014 that live nowhere in git, the DBA exports the deployed definitions and you commit them as evidence:

```sql
-- seat: team — needs the DBA to run this on the test database (ledger-test-db.internal) and hand you the output; commit it under ledger-db/docs/schema/
SET LONG 2000000 PAGESIZE 0
SELECT DBMS_METADATA.GET_DDL('PACKAGE', 'PKG_SETTLE', 'LEDGER') FROM DUAL;
SELECT DBMS_METADATA.GET_DDL('TABLE', 'SETTLEMENT_POSTING', 'LEDGER') FROM DUAL;
```

Once `docs/schema/pkg_settle.sql` is in the repo, "`PKG_SETTLE.POST_BATCH` rounds with `ROUND(v_amount, 2)`" gets a citation `(docs/schema/pkg_settle.sql:214)` — and the question of why Java rounds half-even while the package rounds Oracle's way becomes a cited question for Priya, not a rumour.

:::caution[The history lies before 2021]
The estate moved from Bitbucket to GitHub in 2021 with squashed history. `git log` on anything older shows one migration commit and one author. "Untouched since 2018" is a claim the map can make only for files whose last change is *after* the migration; for the rest it says "no change since the 2021 migration commit". [Inventory the Estate](/kt/inventory-the-estate/) has the same caveat for bus factor.
:::

## The review gate

The map is a `DRAFT` until a named expert has stamped it, and the stamp is a PR approval — a git event with a name and a date on it. The reviewer's job is designed to fit thirty minutes: **read the citations, not the prose.** Priya doesn't judge whether the paragraph about settlement is well written; she opens ten pointers and checks that each line says what its sentence says. This is the checklist, copyable, and it goes in the PR body:

```markdown
# Generated-doc review gate — docs/ARCHITECTURE.md
Reviewer: <named expert>  ·  Time box: 30 minutes  ·  Approval = the stamp

- [ ] Every factual claim ends with `(path:line)`; anything that can't is under "## Unverified" — a bare claim is a defect, not a style issue
- [ ] Spot-check ten citations, not the prose: the entry-point table, three hops of the request path, one integration, one "surprise". The line says what the sentence says
- [ ] Nothing cites `target/`, a Confluence page, a README, or a comment — code and committed schema only
- [ ] "## Unverified" is non-empty. For a repo this size, an empty one means the agent guessed
- [ ] "No callers found" is never written as "unused"; each such finding names where the search looked
- [ ] The build/toolchain sentence names which profile CI runs and cites the workflow file
- [ ] "## Questions for the expert" contains only things the code cannot answer (why, history, intent)
- [ ] Under 400 lines, and you got through it inside the time box — if not, the map is too big, not you too slow
- [ ] Corrections are review comments on the line ("wrong: the rate comes from the cache, not the DAO"), never a rewrite by the expert
- [ ] On approval: label `kt:draft` → `kt:stamped`; status line and the `CLAUDE.md` architecture line updated with STAMPED <date> by <name>
```

The mechanics. Open the PR as a draft with the label and the reviewer; the body is the checklist above plus the one sentence that tells Priya what she's being asked for:

```bash
# seat: team
cd ~/ledger/ledger-core
git switch -c kt/map-ledger-core
git add docs/ARCHITECTURE.md docs/decisions/ CLAUDE.md .claude/skills/map-repo/SKILL.md .claude/agents/repo-question.md
git commit -m "docs: DRAFT architecture map of ledger-core — generated, every claim cited"
git push -u origin kt/map-ledger-core
gh pr create --draft --label kt:draft --reviewer priya-payments \
  --title "DRAFT: ledger-core architecture map — Priya, 30 minutes on the citations" \
  --body-file .github/kt-review-gate.md
```

```console
$ gh pr create --draft --label kt:draft --reviewer priya-payments --title "…" --body-file .github/kt-review-gate.md
Creating draft pull request for kt/map-ledger-core into main in payments/ledger-core

https://github.com/payments/ledger-core/pull/418
```

That URL is the artifact; it's what goes in the calendar invite. Priya leaves comments on lines. Dana — or a session pointed at the comments — applies the corrections; **the expert never types the fix.** When she approves, flip the two status lines (the map's first line becomes `**Status: STAMPED 2026-09-12 by Priya (PR #418).**`, the `CLAUDE.md` line likewise), push, take the one-click re-approval, and merge:

```bash
# seat: team
gh pr edit 418 --remove-label kt:draft --add-label kt:stamped
gh pr ready 418
gh pr merge 418 --squash
```

Make the ownership structural so the next change to the map also needs an expert, whoever opens it:

```text
# .github/CODEOWNERS — a change under docs/ requests an expert's review automatically
/docs/  @priya-payments @marcus-payments
```

:::tip[Good citizen]
Thirty minutes is the budget, and the map is sized to it: under 400 lines, citations to open rather than paragraphs to judge, corrections as comments rather than a rewrite. Sending "please have a look at the architecture doc" with forty pages and no checklist spends Priya's hour and produces nothing — she won't finish, and she shouldn't. If the map ran long, split the review by section across two experts (Marcus takes Data and Integrations), never extend the time box. [The citizenship contract](/kt/overview/#the-citizenship-contract) is the long form.
:::

## Output layout

Three files come out of a map, and they live in the repo next to the code they describe — never only in a chat transcript, never only in Confluence:

```text
ledger-core/
├── CLAUDE.md                          # the standing orders; imports the map (below)
├── docs/
│   ├── ARCHITECTURE.md                # the map — DRAFT until stamped; under 400 lines
│   └── decisions/
│       └── 0000-questions-for-the-expert.md   # seeded from the map's last section
├── .claude/
│   ├── skills/map-repo/SKILL.md       # the skill, so the next map runs the same way
│   ├── agents/repo-question.md        # the per-question subagent
│   └── settings.json                  # the Day-1 baseline, unchanged
└── .github/CODEOWNERS                 # the /docs/ line
```

**`docs/ARCHITECTURE.md`** is the map. **`CLAUDE.md`** is the three-section file from the [Day-1 Checklist](/start/day-1-checklist/) — *what this is*, *how to work here*, *what not to do* — and the map changes one line of it: the architecture line becomes an `@` import, so every future session in the repo loads the map without being asked. The site's template, shown for `ledger-api` (the `ledger-core` version differs only in the first paragraph and the folder named under *What not to do*):

```markdown
# ledger-api

## What this is

Java 17 — the `jdk8` Maven profile is legacy and CI does not run it. Reads and

  tests need `LEDGER_TEST_DB` set (see docs/ARCHITECTURE.md, "Build, run, test").
- Layout: controllers in `src/main/java/com/ledger/api/web`, DTOs in
  `src/main/java/com/ledger/api/dto`. No business logic in controllers — it

- Do not edit anything under `src/main/java/com/ledger/api/legacy/` — scheduled

  dependency job flags unexplained additions.

```

The `@docs/ARCHITECTURE.md` import has a cost, and it's the reason for the 400-line cap: an imported file is in the context on every turn of every session in the repo. Four hundred lines is a few thousand tokens — cached after the first turn, so cheap, but a floor paid on every question Sam asks; a 2,000-line map would tax every session and still not get reviewed. Until the stamp exists, the line reads `Architecture: docs/ARCHITECTURE.md — DRAFT, not yet stamped; treat every architectural claim as unverified`, without the `@` — never write a stamp that hasn't happened. [CLAUDE.md: The Standing Orders](/toolkit/claude-md/) owns how imports and the memory hierarchy work.

**`docs/decisions/`** starts with one file: the map's "Questions for the expert", verbatim, as `0000-questions-for-the-expert.md`. Why `HALF_EVEN` in Java and `ROUND` in PL/SQL, whether Jenkins still runs, why `ManualAdjustmentPoster` is wired by XML — that's the agenda for [the expert session](/kt/expert-interviews/), and each answer becomes a decision record in the same folder. The map found the questions; only Priya has the answers.

## The cost shape

The arithmetic, with placeholders — the rates change and the [costs page](https://code.claude.com/docs/en/costs) is the source of truth:

```text
characters read     ≈ 5–10% of 410,000 lines × ~40 chars/line   ≈ 0.8–1.6 million characters
tool-result tokens  ≈ characters read ÷ ~4                       ≈ 200,000–400,000 tokens, spread across turns and subagents
cost ≈ (fresh input × input rate) + (output × output rate) + (cache writes × write rate) + (cache reads × read rate)
```

Two things shape it. Each subagent pays for its own window and hands back sixty lines, so the parent's context stays small; and every turn re-sends the prefix, so `--max-turns 60` is a cost bound as much as a safety bound. Don't estimate what you can measure — the run's own JSON has the number:

```bash
# seat: team
jq '{num_turns, total_cost_usd, is_error, denials: (.permission_denials | length)}' map-run.json
```

```console
$ jq '{num_turns, total_cost_usd, is_error, denials: (.permission_denials | length)}' map-run.json
{
  "num_turns": 47,
  "total_cost_usd": 3.62,
  "is_error": false,
  "denials": 0
}
```

`total_cost_usd` is the figure that goes in the ledger; `num_turns` under the cap and `denials` at zero say the run converged without wanting a tool it wasn't given. Record the first map's cost and set the next repo's `--max-budget-usd` from it, not from a guess — [Cost and Governance](/overnight-qa/cost-and-governance/) has the per-job shapes.

## Three trade-offs

| One `ARCHITECTURE.md` | Many documents (one per module) |
|---|---|
| **You gain:** one import, one review, one freshness run; Sam reads one file; the 400-line cap forces the map to say what matters | **You gain:** each document fits its module's expert; deeper coverage of a 410k-LOC repo |
| **You pay:** breadth over depth; the request path is one request, not twelve | **You pay:** N reviews, N imports (or a session that loads none), and a map nobody reads end to end |
| **Rule:** one per repo, always. Depth goes in `docs/decisions/` and in the module `CLAUDE.md` files that load lazily | |

| `CLAUDE.md` alone | `CLAUDE.md` + `.claude/rules/*.md` |
|---|---|
| **You gain:** one file to review, one file Sam reads, the three sections everyone knows | **You gain:** path-scoped rules (`paths:` frontmatter with globs) load only when the session touches matching files — the `legacy/` rules cost nothing in a session about FX |
| **You pay:** every rule loads in every session, so the file must stay short | **You pay:** rules spread across files; the "never invent a name" rule must stay global or it's silently absent |
| **Rule:** three sections in `CLAUDE.md`; move a rule to `.claude/rules/` only when it applies to a path, not to the repo | |

| `sonnet` for the map | `opus` for the map |
|---|---|
| **You gain:** search-and-cite at the default model's cost; the eight subagents run cheaply in parallel | **You gain:** better synthesis when a question spans many files — the request path through twelve hops, the DI wiring across XML and annotations |
| **You pay:** the occasional hop the reviewer has to add; a "surprises" list that's complete but flat | **You pay:** the same tokens at a higher rate, for a document whose value is its citations, which either model produces |
| **Rule:** `sonnet` for every repo map; `opus` for [the system map](/kt/mapping-the-system/), which is synthesis over twenty-three summaries | |
