You are here if: Sam starts Monday; or you want one verified artifact before reading eleven pages; or you want to try the method on the lowest-stakes repo before proposing it for `ledger-core`.

Here is the smallest knowledge-transfer artifact that is actually *verified* — one repo, one `docs/ARCHITECTURE.md` with a `path:line` citation on every claim, one expert's stamp — and, at the end, the honest list of what it deliberately doesn't do. Ninety minutes assumes the gate passes: ten for the gate, twenty for the run (you read the skill while it works), twenty to read and spot-check the output, thirty for the expert, ten for the labels and the seed. If the gate fails, it just saved you the thirty minutes of Priya's time you'd have spent on a map of the wrong thing, which is a better use of the ninety.

The subject is `ledger-api`: 35,000 lines, a Spring Boot 2.7 facade in front of `ledger-core`, and the repo new hires touch first. It's the right first subject for three reasons — it's small enough that one run maps all of it, it's where Sam's Monday starts, and a facade's map is mostly *edges* (what it calls, what calls it), which is exactly the knowledge nobody has written down. Substitute your names throughout; the workspace is `~/ledger/`, as on the [Day-1 Checklist](/start/day-1-checklist/).

## The gate: four checks

Each is one command. Any failure → stop, follow the link, come back.

**1. Policy allows this repo's source to go to the approved deployment.** Two halves. The first is a sentence with a ticket number on it — *`ledger-api` source may be sent to the Claude deployment the platform team operates* — and if you can't point at where that's written, [How to find out what yours says](/start/working-within-policy/#how-to-find-out-what-yours-says) is ten minutes. The second half is that your credential actually reaches that deployment from this repo:

```bash
# seat: team
cd ~/ledger/ledger-api
claude -p "Reply with the single word: ready" --max-turns 1 --bare
```

```console
$ claude -p "Reply with the single word: ready" --max-turns 1 --bare
ready
```

`--bare` skips `CLAUDE.md`, hooks, and skills so the check tests only the credential path; `--max-turns 1` means it can't wander. Anything but `ready` — an authentication error, a hang, a proxy message — → [Working Within Policy](/start/working-within-policy/), stop. The map sends the repo's source to a model; the gate is where you confirm that's allowed, not the PR review afterwards.

**2. You can clone it and its build runs.** The skill cites the build files and may run `./mvnw` to confirm what it reads; a build that doesn't run on your laptop produces a "Build, run, test" section that is a guess with a citation on it:

```bash
# seat: team
gh repo clone payments/ledger-api ~/ledger/ledger-api
cd ~/ledger/ledger-api
./mvnw -q -DskipTests package && echo "BUILD OK"
```

```console
$ ./mvnw -q -DskipTests package && echo "BUILD OK"
BUILD OK
```

`-q` keeps Maven quiet, so `BUILD OK` is the only line you should see. A stack trace instead means the build needs something the README didn't mention — a toolchain, an internal artifact repository, a `settings.xml` — and you fix that first, because Sam hits the same wall on Monday and the map should say what it is. (`ledger-api` carries a `jdk8` Maven profile as well as the Java 17 default; saying which one CI actually runs is part of the skill's job.)

**3. Priya or Marcus has thirty minutes booked this week.** Booked — in the calendar, with the PR link in the invite — not "she said she'd look." The stamp is a PR approval, so the link in the invite is the PR, and the PR can exist before the map does: open it now, empty, so the invite points at something real. The expert for `ledger-api` is Priya, because the facade's edges all lead into her settlement engine:

```bash
# seat: team
cd ~/ledger/ledger-api
git checkout -b kt/map-ledger-api
git commit --allow-empty -m "KT: repo map for ledger-api (DRAFT — map to follow)"
git push -u origin kt/map-ledger-api
gh pr create --draft \
  --title "KT: repo map for ledger-api (DRAFT)" \
  --body "docs/ARCHITECTURE.md generated by the map-repo skill; every claim cites path:line. Priya — 30-minute stamp session booked; please read the citations, not the prose, and correct as inline comments." \
  --reviewer priya-payments
```

```console
$ gh pr create --draft --title "KT: repo map for ledger-api (DRAFT)" --body "…" --reviewer priya-payments
Creating draft pull request for kt/map-ledger-api into main in payments/ledger-api

https://github.com/payments/ledger-api/pull/418
```

That URL goes in the calendar invite, titled "Stamp: ledger-api map (30 min)". If neither expert has thirty minutes this week, the map can still be generated — but it stays `DRAFT`, Sam is told it's a draft, and you don't call it done. **A map without a stamp is a plausible document, and plausible is the failure mode.**

**4. A place for the output.** The doc lives at `docs/ARCHITECTURE.md` in the repo — not in Confluence, not in a chat transcript — because the repo is the source of truth and the nightly citation check reads `docs/**/*.md`. The labels are how the team, and later the freshness job, tell a draft from a stamped doc:

```bash
# seat: team
mkdir -p docs
gh label create kt:draft --color FBCA04 --description "AI-generated; not yet reviewed by a named expert" --force
gh label create kt:stamped --color 0E8A16 --description "Reviewed and approved by a named expert (PR approval = stamp)" --force
gh pr edit 418 --add-label kt:draft
```

```console
$ gh label create kt:draft --color FBCA04 --description "…" --force
✓ Label "kt:draft" created in payments/ledger-api
$ gh label create kt:stamped --color 0E8A16 --description "…" --force
✓ Label "kt:stamped" created in payments/ledger-api
$ gh pr edit 418 --add-label kt:draft
https://github.com/payments/ledger-api/pull/418
```

`--force` makes the label commands safe to rerun in the next repo. Gate passed; the rest is the recipe.

## The recipe

Four steps: the standing orders, the skill, the run, the reading. The recipe's proof step is the stamp session after it — everything before that exists to make thirty minutes of an expert's time enough.

### 1. Standing orders

If you did the Day-1 checklist yesterday, `ledger-api` already has a `CLAUDE.md` with the three sections and an honest architecture line, and you skip this step. If not, generate the starter and reshape it — the template and what to edit are on [the checklist](/start/day-1-checklist/#5-a-claudemd-with-the-three-sections):

```bash
# seat: team
cd ~/ledger/ledger-api
claude
```

```text
> /init
```

The one line that matters today is the "not found" rule — *search first, cite `path:line`, and if you cannot find it say so rather than guessing* — because the skill below inherits it. `CLAUDE.md` loads into every session in the repo; the mechanics are on [CLAUDE.md: The Standing Orders](/toolkit/claude-md/).

### 2. The skill

A skill is a procedure you invoke by name, stored as a markdown file the model reads when you call it. This is the site's `map-repo` skill, in full — commit it at `.claude/skills/map-repo/SKILL.md`; the reasoning per rule follows it:

```markdown
---
name: map-repo
description: Map this repository into docs/ARCHITECTURE.md (DRAFT) — entry points, request path, data model, integrations, build & run, surprises — every claim cited path:line, unknowns listed as unknowns. Use when onboarding or when asked "how does this repo work".
disable-model-invocation: true
allowed-tools: Read Grep Glob Bash(./mvnw *) Bash(git log *) Bash(find *)
---
You are mapping this repository for a senior engineer joining the team who has
never seen it. Write `docs/ARCHITECTURE.md`. Its first line is:
`**Status: DRAFT — not yet reviewed by a named expert.**`

Rules that override everything else:
1. Every factual claim ends with a citation `(path:line)` or `(path:line-line)`.
   A claim you cannot cite goes under "## Unverified" with what would confirm it.
2. Search, don't read: use Grep and Glob to find things; read only the files you
   cite. This repository may be very large.
3. "No callers found" is a finding; "unused" is a conclusion. Report the finding.
4. Two toolchains may coexist (Java 8 and 17 profiles, .NET Framework and .NET 8).
   Say which one CI actually runs, citing the workflow or build file.
5. Never invent a class, method, table, queue, or endpoint name. If a name
   appears only in documentation and not in code, say exactly that.

Answer these eight questions, each as a `##` section, in this order:
1. What is this, in one paragraph — and what is it NOT (what lives in
   neighbouring repositories)?
2. Entry points — every way execution starts: HTTP endpoints, message listeners,
   scheduled jobs, CLI mains. A table: entry → handler `path:line` → what it
   calls next.
3. The request path — trace ONE representative request end to end, file by file.
4. Data — the domain model and where it is persisted; every table and queue
   touched, with the code that touches it.
5. Integrations — every external system (databases, queues, HTTP clients, file
   drops): the config key, the code, the direction of data.
6. Build, run, test — the exact commands from the build files and CI, and what
   they require (environment variables, services, credentials by name only).
7. Things that will surprise you — anything a senior engineer would want to be
   warned about: dead-looking code with live callers, reflection or DI wiring,
   generated code, feature flags, dual toolchains, time-zone handling.
8. Safe places to make a first change — three candidates with test coverage,
   cited.

Then two more sections: "## Unverified" and "## Questions for the expert" —
the things only a human can answer (why, history, intent).

Keep the whole file under 400 lines. Prose is cheap; citations are the product.
```

The frontmatter first. `disable-model-invocation: true` means only a human can start this — mapping a repo costs real money and writes a file, and you don't want it triggered because someone asked "how does this repo work?" in passing. `allowed-tools` pre-approves reading, searching, the build, `git log`, and `find` — and nothing else, so the skill cannot push, delete, or fetch whatever a prompt says; what a skill *can't* do never needs a sentence asking it not to. Where skills live and how `/map-repo` resolves is on [Skills: Procedures You Can Invoke](/toolkit/skills/).

Then the five rules that override everything else, each with its reason:

1. **Every claim cites `path:line`.** This is the whole method. Priya can check "does `SettlementController.java:44` say what this sentence says" in twenty seconds; she cannot check "is this paragraph about settlement true" without re-reading the module. Citations turn her thirty minutes into a review of evidence rather than prose — and they are what the nightly job can check later, because a script can verify a pointer and can't verify a paragraph.
2. **Search, don't read.** Thirty-five thousand lines would fit in the model's window; 410,000 in `ledger-core` would not, and the skill is the same file for both. Searching first also makes the map cheaper and, oddly, better: a model that has read everything summarizes; a model that searched for the request path traced it.
3. **"No callers found" is a finding; "unused" is a conclusion.** `ledger-shared` has forty classes nobody has opened since 2018 and every one of them is reachable by reflection or a scheduled job until proven otherwise. The rule keeps the model on the side of the line it can defend.
4. **Two toolchains may coexist — say which one CI runs, citing the workflow.** A map that says "Java 8 and 17" is true and useless; a map that says "Java 17 — `.github/workflows/ci.yml:23`; the `jdk8` profile exists in `pom.xml:112` and CI never runs it" is what Sam needs.
5. **Never invent a name.** The failure this prevents is `FxConversionService` — a class that doesn't exist, named the way this codebase names classes, described with total confidence ([why it happens](/start/how-agentic-coding-works/#why-it-makes-things-up)). "Appears only in documentation, not in code" is a sentence Sam can act on; a plausible name costs an afternoon.

The eight questions are the ones a senior engineer asks on their first day; what a good answer to each looks like, with `ledger-core` examples, is on [Mapping One Repo](/kt/mapping-a-repo/). Today you only need to recognise a good one when you see it.

### 3. The run

Interactive, so you can watch it work the first time:

```bash
# seat: team
cd ~/ledger/ledger-api
claude
```

```text
> /map-repo
```

Expect fifteen to twenty-five minutes and one permission prompt — when the skill writes `docs/ARCHITECTURE.md`, because the Day-1 baseline allows reads and the build but not writes. Approve it; that prompt is the fence doing its job. While it runs, reread the skill with the reasoning above in mind, and don't answer questions on its behalf: if the model asks you something it should have searched for, say "search for it."

The headless equivalent produces the same file plus a receipt, and it's the form the rest of the estate will run in — the same command in a loop over twenty-three repos:

```bash
# seat: team
claude -p "/map-repo" \
  --permission-mode acceptEdits \
  --allowedTools "Read,Grep,Glob,Write,Edit,Bash(./mvnw *),Bash(git log *),Bash(find *)" \
  --max-turns 60 \
  --max-budget-usd 8 \
  --model sonnet \
  --output-format json > map-run.json
```

`--permission-mode acceptEdits` lets it write the doc without a prompt nobody is there to answer; `--max-turns 60` and `--max-budget-usd 8` are the site's defaults for this skill, because a map that hasn't converged in sixty turns is looping, and a cheap loop can run under a budget for a long time; `--model sonnet` because mapping is search-and-cite, not synthesis — `opus` is for the system map. The receipt, read field by field the first time:

```bash
# seat: team
jq '{is_error, num_turns, total_cost_usd, denials: (.permission_denials | length)}' map-run.json
```

```console
$ jq '{is_error, num_turns, total_cost_usd, denials: (.permission_denials | length)}' map-run.json
{
  "is_error": false,
  "num_turns": 41,
  "total_cost_usd": 2.84,
  "denials": 0
}
```

`is_error` false means the run finished on its own rather than being stopped; `num_turns` 41 is well under the cap, so it converged; `total_cost_usd` is the number you record rather than estimate; `denials` 0 means it never asked for a tool outside the allowlist — a non-zero count here is worth reading, because it tells you what the model *wanted* to do. The flags and the full JSON shape are on [Headless Mode and the Agent SDK](/toolkit/headless-and-sdk/). The trade between the two forms: interactive lets you see the search strategy and answer the odd question; headless gives you the receipt and the repeatability. Do the first one interactively, every later one headless.

### 4. Read the output, section by section

Open `docs/ARCHITECTURE.md`. The first line must be the DRAFT status line; if it isn't, the skill didn't run and you're reading something else. Then read it in order, knowing what good looks like. An excerpt of what came back for `ledger-api`:

```markdown
**Status: DRAFT — not yet reviewed by a named expert.**

## 1. What this is
ledger-api is a Spring Boot 2.7 REST facade (pom.xml:9) over ledger-core, which it calls
over HTTP via LedgerCoreClient (src/main/java/com/ledger/api/client/LedgerCoreClient.java:57).
It has no JDBC datasource of its own — no DataSource bean and no spring.datasource key under
src/main (src/main/resources/application.yml:1-64) — and no MQ code (no javax.jms or com.ibm.mq
imports under src/main). It is NOT the settlement engine: amounts, FX, and posting live in ledger-core.

## 2. Entry points
| Entry | Handler | Calls next |
|---|---|---|
| POST /settlements | SettlementController.create (src/main/java/com/ledger/api/web/SettlementController.java:44) | LedgerCoreClient.postSettlement (src/main/java/com/ledger/api/client/LedgerCoreClient.java:88) |
| GET /settlements/{id} | SettlementController.get (src/main/java/com/ledger/api/web/SettlementController.java:71) | LedgerCoreClient.getSettlement (src/main/java/com/ledger/api/client/LedgerCoreClient.java:104) |
| @Scheduled 02:30 | LegacyExportJob.run (src/main/java/com/ledger/api/legacy/LegacyExportJob.java:29) | writes /var/ledger/export (src/main/java/com/ledger/api/legacy/LegacyExportJob.java:52) |
…
## 7. Things that will surprise you
- src/main/java/com/ledger/api/legacy/ has no callers from web/ (Grep "legacy\." under
  src/main/java/com/ledger/api/web: 0 matches) but LegacyExportJob is @Scheduled
  (src/main/java/com/ledger/api/legacy/LegacyExportJob.java:29), so it runs every night.
  No callers found is not the same as unused.
- Both toolchains are in the build: profile jdk8 (pom.xml:112). CI runs Java 17 only
  (.github/workflows/ci.yml:23).
…
## Unverified
- Whether ledger-core's write endpoint is the same host as its read endpoint: application.yml
  has one key, ledger.core.url (src/main/resources/application.yml:18); LedgerCoreClient has a
  separate writeUrl field defaulted to the same value (src/main/java/com/ledger/api/client/LedgerCoreClient.java:61).
  Would confirm: the environment ledger-api is deployed with.

## Questions for the expert
- Why does legacy/LegacyExportJob still run nightly, and what reads /var/ledger/export?
- Is the jdk8 profile needed by any consumer, or can it be deleted?
- TenantFilter requires an X-Ledger-Tenant header (src/main/java/com/ledger/api/web/TenantFilter.java:33)
  and nothing in this repository sets it — who does?
```

What good looks like, section by section: **every sentence ends in a pointer** — including the negative ones ("no `DataSource` bean under `src/main`" is a claim, and the search that backs it is the citation); **"Unverified" is not empty** — an empty one means the model either didn't try or is overstating what it knows, and both are worse than a list; **"Questions for the expert" are *why* questions** — anything answerable by search should have been searched, and a "where" question in this section is a sign the run stopped early. What bad looks like: a paragraph with no pointer (label it `(inference)` yourself before Priya sees it, or delete it), a class name you can't find (`grep -rn "FxConversionService" src/` returns nothing → [It Made Things Up](/troubleshooting/it-made-things-up/), rerun), and a "Build, run, test" section describing commands the repo doesn't have.

Before you spend the expert's thirty minutes, spend three of your own. Pick three citations — one from a section you understand and two you don't — and open the lines:

```bash
# seat: team
sed -n '44p' src/main/java/com/ledger/api/web/SettlementController.java
sed -n '29p' src/main/java/com/ledger/api/legacy/LegacyExportJob.java
sed -n '23p' .github/workflows/ci.yml
```

```console
$ sed -n '44p' src/main/java/com/ledger/api/web/SettlementController.java
    @PostMapping("/settlements")
$ sed -n '29p' src/main/java/com/ledger/api/legacy/LegacyExportJob.java
    @Scheduled(cron = "0 30 2 * * *")
$ sed -n '23p' .github/workflows/ci.yml
          java-version: "17"
```

Three for three means the citations are load-bearing and Priya's time will go on *meaning*, not on catching the model. One wrong out of three means rerun before the session: the recipe's proof step is the stamp, and a stamp on a doc with broken pointers stamps the wrong thing.

:::tip[Good citizen]
Don't send the expert the document. Send the PR, with the "Questions for the expert" section pasted at the top of the description and the sentence "read the citations, not the prose." A document she reads top to bottom is a forty-minute job she won't finish; a list of pointers to click and three questions to answer is thirty minutes she'll actually give you. The [citizenship contract](/kt/overview/#the-citizenship-contract) is the reason; this is what it looks like on a Wednesday.
:::

## The thirty-minute stamp session

Commit the map to the branch you opened at the gate, and take the PR out of draft — the calendar invite already points at it:

```bash
# seat: team
git add docs/ARCHITECTURE.md .claude/skills/map-repo/SKILL.md
git commit -m "KT: ARCHITECTURE.md for ledger-api (DRAFT, generated by map-repo; 38 citations)"
git push
gh pr ready 418
```

```console
$ gh pr ready 418
✓ Pull request payments/ledger-api#418 is marked as "ready for review"
```

The session has three rules, and you run it, not Priya:

- **She reads the citations, not the prose.** Section by section, she opens the cited lines — the PR's "Files changed" view makes every `path:line` a click — and says whether the sentence attached to each is true. She doesn't read the paragraphs for style, completeness, or anything else. If a section is fine, she says "fine" and moves on.
- **Corrections are review comments, not conversation.** Every correction lands as an inline comment on the line it concerns, in her words, while you're in the room. You fix the text in the session or immediately after; she doesn't edit the file and she types nothing but the comments. What only she knows arrives the same way — and since it can't cite code, it's cited to *her*:

```text
Priya, review of PR #418, comment on docs/ARCHITECTURE.md §3:
  The trace is right. Add to §7: the retry on 503 in LedgerCoreClient.postSettlement
  (LedgerCoreClient.java:88) is what caused the 2023 double-post — settlements are NOT
  idempotent on the core side. Sam should know that before touching the client.

Priya, review of PR #418, comment on §2:
  GET /settlements/{id} is blocked at the gateway in prod — keep the row, add
  "(blocked upstream — Priya, PR #418)". The code is live; the route isn't.

Priya, review of PR #418, comment on "Questions for the expert":
  jdk8 profile: ledger-tools-replay still builds against it until Q1. Don't delete.
  LegacyExportJob: ask Marcus. I don't know either.
```

  The doc's version of each becomes a sentence with `(Priya, review of PR #418)` where the `path:line` would be — a named, dated, attributable source is evidence of a different kind, and it's labelled as such. "Ask Marcus" becomes a line in "Questions for the expert" with his name on it; that list is the seed of the [expert sessions](/kt/expert-interviews/) page.
- **Merge is the stamp.** When she has been through the sections and her comments are resolved, she approves. You update the status line, flip the label, and merge — and the stamp is now a git event with a name and a date on it rather than a feeling:

```bash
# seat: team
sed -i '1s/.*/**Status: STAMPED 2026-09-12 by Priya — PR #418. Sections marked Unverified are still unverified.**/' docs/ARCHITECTURE.md
git commit -am "KT: ARCHITECTURE.md stamped by Priya (PR #418)" && git push
gh pr edit 418 --remove-label kt:draft --add-label kt:stamped
gh pr merge 418 --squash
```

```console
$ gh pr edit 418 --remove-label kt:draft --add-label kt:stamped
https://github.com/payments/ledger-api/pull/418
$ gh pr merge 418 --squash
✓ Squashed and merged pull request payments/ledger-api#418
```

Then make `CLAUDE.md` tell every future session that the map exists and how far to trust it — the one line the Day-1 checklist left honest, now true. This is the site's template ([in full on the checklist](/start/day-1-checklist/#5-a-claudemd-with-the-three-sections)), excerpted:

```markdown
# ledger-api

## What this is
# …
Architecture: @docs/ARCHITECTURE.md (STAMPED 2026-09-12 by Priya — treat as
true and cite it; anything not in it is unknown, not inferred).
# …
```

The `@` import loads the map into every session in the repo, so Sam's first question on Monday is answered from a stamped document; the parenthesis tells the model the difference between what's in the map (cite it) and what isn't (say "unknown"). A stamp means *the citations she checked hold and nothing she read is wrong*. It doesn't mean complete — the "Unverified" section survives the stamp, labelled, and that's correct.

## The one-sentence measurement seed

Two minutes that turn this from "a thing we generated" into "a thing we can judge." Write it in the description of PR #418, where it sits next to the artifact:

> **Sam will open a meaningful PR in ≤ ___ weeks.**

"Meaningful" means a change to behaviour someone outside the team can see, reviewed by someone other than the expert. Can't fill the blank with a target? Then fill it with the baseline: Sam's predecessor took **11 weeks** — write `PROVISIONAL: baseline 11 weeks (predecessor); target to be set after Sam's first month` and leave it. That sentence is the seed [Measuring KT](/kt/measurement-and-governance/) grows into the program's first real number, and the difference, starting today, between a target and a hope.

## Watch it for a week

Three things to count, each with what-good-looks-like and what to do if not:

| Watch | How | Healthy | If not |
|---|---|---|---|
| Does Sam's first question get answered by the doc? | Every question Sam asks in the channel or a session, tally: *answered by the map* / *not in the map* / *map was wrong* | At least half answered by the map in week one; the "not in the map" questions are mostly about *other* repos | Mostly "not in the map" about `ledger-api` itself → a section is missing; rerun that one question alone. Any "map was wrong" → fix it, and count it toward the next row |
| How many corrections did the expert make? | Open PR #418 and count Priya's inline comments; `gh pr view 418 --json reviews --jq '.reviews[].state'` lists her review passes | 3–10. Some corrections means she read it; zero means she didn't, or the repo is trivial | More than 20 → the map was too big for thirty minutes, or the model invented; split it, or rerun the worst section with the [review gate](/kt/mapping-a-repo/#the-review-gate) in hand |
| How long did the stamp take? | From `gh pr ready` to her approval, on the PR's timeline | ≤ 30 minutes, in one sitting | Two sittings, or two hours → the unit of review was too large; the [four questions](/kt/overview/#the-four-questions-before-any-kt-work) say break it until the stamp fits |

A week of this counting is, quietly, the first data for the measurement page: you've started measuring expert-questions-per-week without meaning to. Keep the tally.

:::caution[What this deliberately doesn't do]
Honesty about the recipe's edges — this is L1 of [the maturity ladder](/kt/overview/#the-maturity-ladder), not the destination:

- **One repo.** Twenty-two remain, and nobody has decided which of them matters. → [Inventory the Estate](/kt/inventory-the-estate/)
- **No system picture.** The map says `ledger-api` calls `ledger-core`; it can't say what calls `ledger-api`, or where `LEDGER.SETTLE.IN` enters. The system is the edges. → [Mapping the System](/kt/mapping-the-system/)
