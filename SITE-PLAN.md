# AI Enablement Playbook — site plan (greenfield, first draft 2026-09-10)

## Context

The site owner wants a sister site to [K8s Soup to Nuts](https://github.com/jamiegunn/k8s_soup_to_nuts) — same bones (Astro + Starlight + Pagefind + starlight-blog + self-hosted Mermaid + content lint + GitHub Pages), same voice (plain-language-first, complete commands, tradeoffs stated, many front doors, the reader's seat named on every page), same recurring cast (team `payments`) — for **engineering teams putting AI to work on two problems that actually hurt**:

1. **Knowledge transfer (KT) on a legacy estate.** A large, old, multi-repo codebase whose architecture lives in two long-tenured engineers' heads and a Confluence space nobody trusts. New developers take months to become useful; the experts are the bottleneck for every question; nobody can say what would break if one of them left. The initiative: use AI (Claude Code first) to get what's in the code, the docs, and the heads into something a new hire can *query*, verified by the experts, kept true by CI — and rebuild onboarding around it.
2. **Overnight QA.** Scheduled, unattended agent jobs — GitHub Actions on a cron — that test code and applications while the team sleeps and leave a **morning report** worth ten minutes of a human's attention: what ran, what failed, what's new, what needs a person, what it cost. Reports land in Slack/Teams (the summary), GitHub (issues and draft PRs per finding), and Confluence (the durable page).

**Tooling stance (owner decision):** Claude-first, principles portable. Every technique is shown as a complete, runnable Claude Code recipe (CLI, `CLAUDE.md`, skills, subagents, hooks, MCP, headless mode, the GitHub Action, the Agent SDK) *and* stated once as a tool-agnostic principle, so the site survives a vendor change without a rewrite. Where Copilot or Gemini would do the same job, one sentence says so; no parallel toolchains.

**Runtime stance (owner decision):** overnight jobs run on **scheduled GitHub Actions** (`ubuntu-latest` for anything self-contained; a self-hosted runner for jobs that need the on-prem Oracle test database or an internal staging URL). Kubernetes CronJobs are mentioned once as the alternative and linked to the sister site; not built here.

**Scope of this draft (owner decision):** scaffold + plan + a full first draft of both playbook sections (12 pages each), plus the Start Here section, a reference Toolkit section both playbooks depend on, a symptom-first Troubleshooting section, Learning Paths, About, and three Field Notes. Deep pages deferred are listed at the end.

**What the sister site already owns — link, never re-explain:** GitHub Actions mechanics beyond the scheduled-job specifics (`/ci/github-actions/`, `/ci/reusable-workflows/`, `/ci/testing-in-ci/` on K8s Soup to Nuts), Artifactory, ephemeral clusters, observability and logs, Helm, everything Kubernetes. This site links out with an absolute URL (`https://jamiegunn.github.io/k8s_soup_to_nuts/…`) and stops.

## The reader's seat

**You own your team's workflow — the repos, the CI, the onboarding, the tests — not the enterprise AI platform.** Somewhere in the organization a platform (or "AI enablement", or "developer experience") team owns the Claude deployment: which models are approved, whether the API key comes from Anthropic direct or through Bedrock/Vertex, the managed settings pushed to every laptop, the GitHub org policies, which MCP servers are allowlisted. Security owns the data-boundary policy: what source code, what documents, what customer data may be sent to which model where. You get: Claude Code on your laptop, an API key or provider credentials for CI, a GitHub org with Actions enabled, a Confluence space, and a Slack or Teams channel. That's the deal, and — like the namespace on the sister site — it's a good deal, but most AI tutorials assume you're the one who set all of it up.

:::note[The one rule of this site]
If a technique requires org-admin, a security exception, a budget decision, or a managed-settings change, we say so explicitly and tell you what to ask for and what evidence to bring. If you see advice elsewhere that starts with "just give the agent your prod credentials", that's your cue that the article wasn't written for you.
:::

**Target reader:** a tech lead or senior engineer ("Dana", below) on a delivery team who has been told "make AI work for us" — has used Claude in a chat window, maybe run Claude Code on a side project, has never written a `CLAUDE.md`, has never run an agent unattended, and is rightly nervous about both the cost and the blast radius. Secondary readers: the new hire (Sam) following the onboarding track; the platform/security reviewer reading to decide whether to approve the night shift.

## Readability contract (inherited from the sister site's playbooks, applies to every page)

- **Plain language before any code.** Every page's first section explains its topic from zero. The overviews explain the initiative itself from zero ("knowledge transfer is moving what's in heads, code, and docs into something a new hire can query"; "overnight QA is a bounded agent job that runs while nobody's watching and leaves evidence, not opinions").
- **Every term gets one plain sentence on first use per page**, then a link to the deep page: context window, token, agent loop, tool call, permission mode, MCP, hook, skill, subagent, headless mode, characterization test, mutation score, SARIF, CQL. Links supplement, never substitute, the sentence.
- **No unexplained jargon, no "obviously/simply."** Every formula (token budgets, cost shape, bus factor, mutation score) gets a worked example with the cast's real numbers immediately after.
- **Complete-commands contract:** every command in full — real cast names, explicit paths, no elided flags, no `...` inside a command, no aliases. One plain sentence of *what it does and why you're running it* before; a `console` (or `markdown`/`json`) block of representative output after, with the line(s) to look at called out. `claude -p --output-format json` output is read field by field the first time it appears in a section; a hook's JSON is read field by field the first time it appears.
- **Prompts are first-class artifacts.** Every prompt the site relies on is shown in full, in a `text` fence with a filename comment on line 1 (`# .claude/skills/map-repo/SKILL.md` or `# prompts/nightly-triage.md`), and lives in the repo the reader is building — never pasted ad hoc into a terminal. Where the assembled context matters, a short "What the model sees" aside lists it (CLAUDE.md + these files + this MCP data).
- **The seat marker:** AI work crosses the team/platform/security boundary constantly, so every command block's first line is a comment naming the seat it runs from — `# seat: team` (your laptop or your repo's CI, nothing to ask for), `# seat: team — needs <thing>` (an API key in GitHub secrets, an MCP server allowlisted, a Confluence token — the ask is on the policy page), `# seat: platform — shown so you can read THEIR config, you won't run it` (managed settings, org policy), `# seat: security — their approval, your evidence`. A reader must never discover mid-rollout that a recipe needs a permission they don't have.
- **The why, always:** no flag, prompt line, or recommendation without its reason attached. "`--max-turns 25`" is always "…*because* a triage that hasn't converged in 25 turns is looping, and the budget flag alone won't stop a loop that's cheap per turn."
- **Tradeoffs are stated, not implied:** every meaningful choice (read-only vs write access for the night; Atlassian's hosted MCP vs the community server; Sonnet vs Opus per job; docs-in-repo vs docs-in-Confluence; one big CLAUDE.md vs `.claude/rules/`; characterization tests vs approval tests) carries "what you gain / what you pay" — a two-column mini-table for big decisions, a "The trade:" sentence for small ones.
- **Define → observe → decide, for every measurement:** tokens per run, cost per run, `num_turns`, exit code, mutation score, doc freshness, bus factor, report read rate — each gets a plain definition, the exact command to fetch it, and an "if you see X → it means Y → do Z" rule at first load-bearing use.
- **Every AI claim carries evidence.** Generated documentation cites `path:line`; a finding in the morning report links a log line, a failing test, a screenshot, or a diff. Prose without a pointer is labeled as such ("the model's inference — unverified"). Review test: grep every generated artifact the site shows for a claim without a citation; it must be labeled.
- **The one-sequence rule:** the moment a page reaches "…and here's how CLAUDE.md loading works" (or hooks, MCP config, headless flags, the GitHub Action's inputs), it links to the Toolkit page and stops. The playbooks are about *decisions and workflow*; the Toolkit owns *mechanics*. Review test: grep each playbook page for `--allowedTools`, `settings.json`, `.mcp.json`, `permissionDecision` — every hit is either inside a complete recipe (allowed) or a link (allowed), never an explanation paragraph (not allowed).
- **Version and vendor claims** are phrased "as of September 2026" and come from `docs/research/FACTS-*.md`. Nothing on the retired list in `scripts/lint-content.mjs` may be taught. Prices are never printed; the arithmetic is taught with placeholders and a link to the vendor pricing page.

## The named mental model: The Three Levers (stated once in Start Here, used everywhere)

Every technique on this site pulls one of three levers, and every failure is one of them left unpulled:

1. **Context — what the model can see.** The repo it's pointed at, the `CLAUDE.md` standing orders, the files it has read this session, the Confluence page fetched over MCP, the test output piped in. The model reasons only over what's in the window; most "it made that up" incidents are context failures wearing a confident face.
2. **Tools — what the model can do, and is allowed to do.** Read, search, run a command, edit a file, call an MCP server, open a browser. Permission modes, allow/deny rules, and hooks draw the line between *can* and *may*. Most "it did something scary" incidents are tools with no line drawn.
3. **Proof — how you'll know it was right.** A citation to `path:line`, a test that runs, a diff a human reads, an expert's stamp on a doc, a screenshot in the report. Most "we trusted it and it was wrong" incidents are a missing proof step, not a bad model.

Its diagnostic use (the Troubleshooting overview): when output is bad, ask in order — *could it see what it needed? could it do what it needed (and only that)? did anyone check?* Its design use: every recipe on the site names which levers it pulls and what its proof step is.

## The citizenship contracts (one per playbook, stated once in each overview, enforced everywhere)

**KT edition: The expert's hour is the scarcest resource in the building. Spend tokens to save expert hours — never the reverse.** Priya and Marcus have, between them, about six spare hours a week. Every technique in the KT playbook is judged by one question: does it turn one expert hour into more durable, verified knowledge than that hour would have produced in a meeting? So: the AI writes every first draft; the expert only ever *corrects*; the repo keeps the result; every generated claim carries a `path:line` citation so the expert reviews evidence, not prose; every artifact is labeled `DRAFT` until a named expert stamps it (a PR approval — the stamp is a git event, not a feeling). The recurring `:::tip[Good citizen]` aside appears wherever a technique could burn an expert's hour instead of saving it: a 40-page generated doc nobody will read, an interview with no prepared questions, a "please review this" with no diff.

**Overnight edition: An unattended agent is a new hire with root and no manager. Bound it before you trust it.** The night has no human in the loop, so every safety property must be structural, not behavioural: read-only by default (`--permission-mode plan` or a deny list, never "please don't"); writes only to a branch and a draft PR, never `main`, never production; every run has a cost ceiling *and* a turn cap; every finding links to evidence; every job has a kill switch (a workflow you can disable) and a budget ledger someone reads. A night that can't prove it ran is a night that didn't. The recurring `:::tip[Good citizen]` aside appears wherever a job could spend someone else's money or attention: an unbounded `--max-turns`, a report that repeats yesterday, a job that opens an issue per flaky test, a browser agent pointed at a shared staging environment during someone else's test window.

## The measurement thread (the SLO analogue, runs through both playbooks)

The sister site derives every number from a user promise. Here every initiative derives its *success measure* before its first run, or honestly labels it provisional:

- **KT:** time-to-first-meaningful-PR for a new hire (baseline: Sam's predecessor took 11 weeks); expert-questions-per-week in the team channel (baseline: ~30, of which the experts estimate two-thirds are "where is X / why does Y"); bus factor per critical repo (baseline: `ledger-core` main-dev share 71% Priya); doc freshness (share of ARCHITECTURE.md claims whose cited lines still exist, checked nightly). Target after one quarter: first PR in ≤3 weeks, expert questions halved, no repo above 60% single-author share on the current year's commits, freshness ≥95%.
- **Overnight QA:** report-actioned rate (findings a human did something with ÷ findings reported; baseline none; target ≥50% or the report is noise), mean minutes from report to triage decision (target ≤10 at standup), cost per actioned finding, and signal:noise trend week over week. A night whose report-actioned rate falls below 20% for two weeks is turned off and redesigned, not tuned.
- The **fallback ladder** applies unchanged: (a) measured baseline → target; (b) proxy ("Priya says ~30 questions a week — PROVISIONAL"); (c) floor ("we'll count for two weeks before setting a target" written down with a TODO). Every metric in a governance page requires the level to be stated.

## The organizing frames

**KT playbook — where does it live · how do we get it out · how do we keep it true.** Knowledge lives in three places: the code (what the system *does*), the documents (what someone once *said* it does), and the heads (why it does it that way, and what would break). Each has a different extraction technique — agents mapping repos; agents mining and freshness-scoring Confluence; structured expert sessions with AI-prepared questions and AI-drafted decision records — and one shared destination: the repo, as `CLAUDE.md` + `ARCHITECTURE.md` + `docs/decisions/*.md`, which a nightly job then keeps true. The pipeline drawn once in the overview: **Inventory → Map → Verify → Teach → Keep true.** Every page states which stage it serves.

**Overnight playbook — what question · what evidence · what blast radius.** Three questions before any nightly job: *What question should the night answer?* (not "test everything" — "did yesterday's changes break settlement?"); *What evidence would prove the answer?* (a failing test, a diff, a screenshot, a SARIF row — never a paragraph); *What's the blast radius if the agent is wrong?* (read a log: none; write a test: a PR to review; click through staging: someone else's test data; anything touching prod: not on this site). The anatomy drawn once in the overview and used as the spine of the cheat sheet: **Trigger → Environment → Deterministic phase → Agent phase → Evidence → Report → Human.**
